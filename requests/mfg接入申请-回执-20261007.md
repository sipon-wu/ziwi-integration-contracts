## 四、三个语义问题（Q1/Q2/Q3）逐条答复

### Q1. License 状态枚举映射 —— 建议对齐服务端实际集合

服务端实际可用值（A）：`none | trial | active | expired | revoked`。

**建议映射（mfg 本地扩枚举，倾向采纳你方"扩枚举"方案）**：

| 服务端 | mfg 本地（原） | 建议 mfg 本地（新） | 门禁语义 |
|---|---|---|---|
| `active` | `valid` | `valid` | 放行 |
| `trial` | （无） | `trial` | 放行（可加试用提示） |
| `none` | `null`（未配置） | `none` | **按 §Q2 决定** |
| `expired` | `expired` | `expired` | 限制（只读） |
| `revoked` | （无） | `revoked` | 限制（只读） |

> 结论：**同意 mfg 扩本地枚举为 `none | trial | valid | expired | revoked`**；服务端不必为 mfg 新增枚举（`revoked` 已有代码分支，UI 下拉未列但 API 可写，建议后续把 `revoked` 补进 UI 下拉）。

### Q2. `none` 是否触发降级 —— 服务端**不会**，降级是**客户端**职责

**实测**：A 服务端的离线巡检 `check_deployments()` **只**更新 `Deployment.status = online/offline`，**不改 `License.status`、不阻断、不下发降级指令**。License 状态仅由 admin 人工设定，并随心跳响应回传（`license_status` / `expires_at` / `revoked`）。

**结论**：
1. 服务端侧：`none` **不会**触发任何限制 → staging 开心跳不会被服务端锁。
2. 客户端侧：是否因 `none` 降级，**由 mfg 自行定义**。契约 §D 的降级判据是"连续 24h 失联"，与 License 状态解耦。**建议**：把"失联降级"（通信维度）与"License 失效降级"（授权维度）**分开建模**——
   - `none`：视为**未授权**，限制新建/云端能力（与 expired 同档），或按商务要求放行试运行（需产品拍板）；
   - `expired` / `revoked`：限制（只读）；
   - 失联 24h：另按契约 §D 处理。

   > 这样即使 staging 先建档为 `trial`，也不依赖"服务和善"这一隐含假设。

### Q3. 私有部署离线 License 来源 —— 在服务端 A 上**该问题不成立**

**实测**：A 的 `HeartbeatRequest` schema 为 `{tenant_id, product, version, status, license_status, license_expires_at, details}`——
- **无 `license_issued_at`**，`license_expires_at` 也不参与校验；
- 无"缺失 license 字段则 400"的逻辑（Pydantic 静默忽略额外字段）；
- Deployment 的 `license_issued_at/expires_at` 取自服务端 License 记录（`lic.expires_at or now`）。

**结论**：你方 SDK 的 `_NeedLicense`（400 → 补带 license 重试）分支在服务端 A 上**永不触发**，申请所述"新部署持续报 `needs license info` 而无法注册"在 A 上不会发生。

- **A 模式（当前）**：License 权威源 = **服务端 A 的 admin 后台建档**，mfg 侧两个 env **可留空**（填了也不被消费，仅作客户端自知）。
- **离线 License 文件（内嵌 cloud 公钥）** 属 **B 模式**（cloud `license_key` JWT）能力，A 不支持。

> 若产品需要"断网离线授权文件"能力，应走 B 并明确 `license_key` 下发流程；否则以 A 后台建档 + 心跳回传为唯一权威通道。
