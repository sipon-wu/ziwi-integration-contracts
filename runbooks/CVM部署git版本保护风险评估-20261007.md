# CVM 部署目录接 git 的风险评估（2026-10-07）

> 评估对象：把 `/opt/cloud-idp`（cloud 运营端）与 `/opt/heartbeat`（心跳服务端）纳入 git 版本保护
> 结论：**不建议直接在生产目录 `git init` + `git pull`（方案 B）**；推荐 **方案 C（零凭据 + 部署前 dry-run 校验 + tar 快照回滚）**，并先解决下方 3 个前置问题。
> 评估人：codebuddy｜依据：CVM 实测 + dry-run 差异比对（全程只读，未改任何生产文件）

## 一、实测事实（今日取证）

| # | 事实 | 证据 |
|---|---|---|
| 1 | CVM **有** GitHub SSH key，但只配了 `github-mfg` 别名 | `~/.ssh/config`：`Host github-mfg` → `IdentityFile /root/.ssh/id_ed25519_mfg`；`ssh -T git@github.com` = Permission denied |
| 2 | `/opt/cloud-idp` **无 git**；但 `backend/.git` 存在 | 08-12 的 `init` 快照，**无 remote**，仅 1 commit，无未提交改动（除未跟踪 `CONTRIBUTING.md`） |
| 3 | `/opt/ziwi/mfg` 有完整 git 工作树 | remote `git@github-mfg:sipon-wu/ziwi_mfg.git`，与 GitHub 一致 |
| 4 | **🔴 布局不匹配**：线上是 `backend/app/`，compose `build: ./backend`；新仓 `ziwi_cloud` 是**顶层 `app/`** | dry-run 结果显示 rsync 会 `*deleting backend/app/services/...` 等**整棵 backend 树** |

| 8 | 目录体积：cloud 79M/3201 files；heartbeat 352K/43 files | `du -sh` / `find -type f` |

## 二、方案与风险矩阵

| 方案 | 做法 | 主要风险 | 评价 |
|---|---|---|---|
| **A. 维持现状**（rsync + Mac 枢纽） | 保持 `方案 A`（CVM 不直连 GitHub） | 线上被手工改动无法察觉；无回滚点 | 基线，可接受但缺追溯 |
| **B. 生产目录 git init + pull** | 配 deploy key，CVM 直接 `git pull` | ①**凭据攻击面**：CVM 公网可达（80/443），给机器加 GitHub 凭据会放大入侵后果<br>②**两条真相同步路径**（rsync + git pull）并存 → 真相源混淆，恰是本次事故土壤<br>③**pull 冲突**：服务器上手工改动会阻塞 deploy（rsync 则直接覆盖）<br>④79M/3201 文件每次 pull 成本高<br>⑤与 C 不直连 GitHub 的既定安全策略冲突 | ❌ 不推荐 |
| **C. 零凭据校验 + 快照**（推荐） | 部署前 `rsync --dry-run --itemize-changes` 人工确认；部署后记录 commit SHA；部署前 tar 快照保留 3 份 | 无凭据暴露、无路径冲突；回滚为"解 tar"，秒级 | ✅ 推荐 |

> **关键判断**：`/opt/ziwi/mfg` 已有 git 工作树且能与 GitHub 同步，说明"CVM 不直连 GitHub"并非能力约束，而是既定策略；给它加凭据等于推翻该策略，收益（追溯）可用方案 C 以零成本获得。

## 三、方案 C 的落地动作（零凭据、零攻击面）

1. **部署前置校验**（每次部署必跑，人工过一眼差异清单）
   ```bash
   rsync -azn --itemize-changes --delete <同样的 exclude> \
     /Users/sipon/CodeBuddy/ziwi_cloud/ root@193.112.163.147:/opt/cloud-idp/
   ```
   预期只出现 `.f..t....`（时间戳）与新增文件；**若出现 `*deleting` 或 `>f.st......`（内容变更）必须停下核查**。
2. **部署台账**：部署后在协同仓 `deploy-log/变更记录.md` 记录「仓 + commit SHA + 时间 + 触发原因」。
3. **回滚快照**（部署前）
   ```bash
   ssh root@193.112.163.147 'tar czf /opt/deploy_snapshots/cloud-idp_$(date +%F_%H%M).tar.gz -C /opt cloud-idp --exclude=cloud-idp/backend/keys'
   # 仅保留最近 3 份
   ```
4. **线上-仓库一致性抽查**（每日/部署后）：对 `app/main.py`、`docker-compose.yml`、`heartbeat/backend/app/main.py` 比 sha256。

## 四、动手前必须先解决的 3 个前置问题

| # | 问题 | 建议动作 | 风险 |
|---|---|---|---|
| **P1** | **布局不匹配**：新仓顶层 `app/` vs 线上 `backend/app/`（compose `build: ./backend`） | **推荐 P1-a**：把仓库改为 `backend/` 布局（`app/`、`Dockerfile`、`requirements.txt`、`tests/`、`test_keys/` 移入 `backend/`），使 rsync 变成**纯覆盖**、compose 零改动；同步更新 `CONTRIBUTING.md`/`README.md` 路径。<br>备选 P1-b：改线上 compose 为 `build: .`（需改生产配置 + 重建容器） | P1-a：改仓不动生产，零风险（但要同步文档/CI 路径）<br>P1-b：动生产，需授权与回滚预案 |
| **P2** | `backend/keys/` 冗余明文私钥（未挂载、未使用） | 删除该目录（生效私钥在 docker 卷里，删后应用照常；先确认卷内私钥可正常签发/验签） | 低。删前留 tar 备份 |
| **P3** | compose 硬编码 `PLATFORM_ADMIN_EMAIL=admin@ziwi.cn` 覆盖 env_file 的新邮箱 | 删除 compose `environment` 段中该行（让 env_file 生效），或同步为 `fengliang@ziwi.cn`；`PLATFORM_ADMIN_PASSWORD` 同理应交由 env_file 独占 | 中。改 env 会触发容器 recreate；需确认 DB 中 super_admin 邮箱与此一致（DB 已是 fengliang） |

## 五、明确不做（越权风险）

- 不给 CVM 新增 GitHub 凭据、不改 `/root/.ssh`（方案 B 整体否决）
- 不删除 `backend/.git`（虽是无 remote 的单机快照，但它是 08-12 的历史记录；仅在确认无用后另行请示）
- 不改线上 compose / 不重建容器（属生产红线，须主理人明确指令）
- 不动 `/opt/cloud-secrets/.env` 内容（仅指出与 compose 的覆盖关系）
